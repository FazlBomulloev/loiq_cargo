## 1. Функциональные баги (по результатам живого прогона)

### 🔴 P0-1. Дефолтного овнера `owner@loik.local` невозможно залогинить
- **Что происходит.** `POST /api/v1/auth/staff/login` с `owner@loik.local` → **422** от pydantic v2 + email-validator: `"The part after the @-sign is a special-use or reserved name"`. Bootstrap при этом создаёт овнера именно с этим email (`.env` → `OWNER_EMAIL=owner@loik.local`), т.е. **из коробки овнер существует, но зайти в кабинет никак нельзя**.
- **Где.** `backend/app/schemas/auth.py:StaffLoginRequest` (EmailStr) + `backend/app/bootstrap.py:ensure_owner`.
- **Как чинить.**
  1. Заменить в `.env`: `OWNER_EMAIL=owner@loik.io` (или любой публичный TLD) и обновить его в БД (`UPDATE users SET email='owner@loik.io' WHERE role='owner'`).
  2. Дать сообщение в bootstrap: если email не проходит валидацию — logging.error и не создавать пользователя. Сейчас он молча создаётся «мёртвым».

### 🔴 P0-2. Toast показывает `[object Object]` вместо человеческого сообщения об ошибке
- **Что происходит.** Любая 422 от FastAPI приходит с `detail = [ { loc, msg, ... }, ... ]` (массив). В `frontend/src/lib/api.ts:78-82` берётся `data.detail || data.message` и через `String(msg)` кладётся в `throw new ApiError`. `String([object])` = `[object Object]` → пользователь видит бессмысленный тост. Воспроизведено на `/staff/login` при неверных данных.
- **Как чинить.** В `api.ts` нормализовать `detail`:
```ts
function normDetail(d: unknown): string {
  if (typeof d === 'string') return d
  if (Array.isArray(d)) return d.map((x: any) =>
    typeof x === 'string' ? x : (x?.msg ?? JSON.stringify(x))
  ).join('; ')
  if (d && typeof d === 'object') return (d as any).msg ?? JSON.stringify(d)
  return `Ошибка ${status}`
}
```

### 🟠 P1-3. Клиент, «пропустивший» Telegram, теряет доступ к верификации
- Кабинет клиента (`/app`) показывает пилл «Ожидаем Telegram», но нигде нет кнопки «Привязать сейчас». Пользователь застревает: чтобы дойти до deep-link, нужно выйти, зарегистрироваться заново или переходить руками к боту.
- **Фикс.** Добавить в `ClientLayout` или в `Dashboard` кнопку «Привязать Telegram» → открывает `/register/verify` (или сразу deep-link из `/clients/me/verify-code`).

### 🟠 P1-4. Клиент не может перегенерировать TG-код, обратный API есть
- Эндпоинт `POST /clients/me/verify-code/regenerate` есть, UI нет.

### 🟠 P1-5. Регистрация не защищена от повторных нажатий и авторегистрации
- Нет rate-limit. Скрипт может насоздавать десятки LQ-XXX за секунду → мусорная нумерация + расход телефонов.
- `client_code` **последователен** (`_next_number` в `services/client_codes.py`), угадать соседей тривиально.

### 🟠 P1-6. Гонка при выдаче `client_code`
- `generate_client_code` читает max, ORM пишет — без транзакционного `SELECT ... FOR UPDATE`. Два параллельных `POST /clients/register` могут получить одинаковый код (упадёт по UNIQUE, но 500-ошибка вместо retry).
- **Фикс.** Обернуть выдачу кода в advisory-lock или использовать sequence.

### 🟠 P1-7. Кабинет клиента не даёт ни сменить пароль, ни отредактировать телефон/имя
- Единственные API — под staff (`/clients-admin/{id}`). У клиента нет ни экрана «Профиль», ни `PATCH /clients/me`. Забытый пароль ⇒ поддержка руками.
- **Фикс.** Добавить `PATCH /clients/me` (имя, телефон + требование повторной TG-верификации) и `POST /clients/me/change-password`.

### 🟠 P1-8. Нет «Забыли пароль» — ни для клиента, ни для сотрудника
- Восстановление возможно только через Telegram → сброс. Сейчас нет.

### 🟡 P2-9. Ссылка «Оформить постоянный код клиента →» на калькуляторе видна и для авторизованного клиента
- В `Calculator.tsx:172-177` ссылка `to="/register"` идёт всегда. У залогиненного клиента она бессмысленна. Нужен `getKind()`-guard.

### 🟡 P2-10. Ссылка «Калькулятор» из кабинета клиента ведёт на `/` (публичный шелл)
- В `Dashboard.tsx:91-97` — `<Link to="/">`. Клиент увидит «Стать клиентом»/«В кабинет», хотя логично держать его в контексте кабинета. Как минимум — не разлогинивать. Наша правка PublicShell возвращает его назад по лого, но это дополнительный клик.
- **Идея.** Встроить калькулятор в кабинет как секцию или модалку.

### 🟡 P2-11. `form_input` через React (для внешних инструментов) — Login не срабатывает
- При тестах через Chrome MCP submit кнопка «Войти» не отправляла запрос: `form_input` заполняет `value` без диспатча `input`/`change`. React-state не обновляется → `disabled` кнопки логически осталось true. Пришлось логинить через прямой `fetch`.
- Скорее не баг, а хрупкость. Но говорит о том, что **автотесты через RPA** сломаются. Использовать `data-testid` + управляемые компоненты с onInput.

### 🟡 P2-12. Bot healthcheck постоянно `unhealthy`
- В `docker-compose.yml` у сервиса `bot` наследуется healthcheck из Dockerfile: `curl http://localhost:8000/health`. Бот HTTP-сервер не поднимает → healthcheck всегда падает. Не аварийно, но зашумляет мониторинг.
- **Фикс.** В `docker-compose.yml` у сервиса `bot`:
  ```yaml
  healthcheck:
    test: ["CMD", "python", "-c", "import sys; sys.exit(0)"]
    interval: 30s
  ```
  или `disable: true`.

### 🔵 P3-13. Frontend контейнер тоже `unhealthy`
- `wget -qO- http://localhost/` под nginx-alpine возвращает 200, но wget может отсутствовать/отваливаться. Заменить на `curl -fsS http://127.0.0.1/`.

## 3. Анализ дизайна и рекомендации

### Что уже хорошо

- Единый **дизайн-токен-слой** (`tokens.css`) + Tailwind → консистентность цветов и шрифтов.
- Хорошая палитра: тёплые «крафтовые» тона (`#F5EFDF`, акцент `#B45A2B`) — уникальные, не похоже на бутстрап.
- Продуманная типографика: Inter (sans) + Fraunces (serif, для заголовков) + IBM Plex Mono (для чисел, `tabular-nums`). Это уровень сильно выше среднего для B2B-CRM.
- Табличные утилиты (`.font-mono-nums`, `label-caps`) — правильно.
- KPI-плитки и `Pill` варианты (`ok/warn/crit/info/route`) — удачная система семантических цветов.

### Слабости и что улучшить

**Т1. Только светлая тема.**
`html { color-scheme: light }` жёстко. Аудит `ui-ux-pro-max` рекомендует минимально задекларировать переменные для `@media (prefers-color-scheme: dark)` и использовать `data-theme` для переключения. Иначе пользователи с системным dark теряют глазную комфортность. Разработать **комплементарную dark-палитру** на тех же семантических токенах:
```
--bg-app: #14100B; --bg-elev: #1B160F; --bg-card: #221C13;
--text-primary: #F5EFDF; --line: #3A2F20;
--accent: #E27B45; --accent-strong: #F49765;
```

**Т2. Скучный «шум» вокруг основных таблиц.**
Секции Card оборачивают таблицу в тонкую бежевую рамку — при большом объёме данных они сливаются. Ввести **strong hierarchy**:
- Заголовки таблиц с `bg-elev` и sticky-top при скролле.
- Zebra-строки (`odd:bg-elev/50`) — читаемее при 20+ строках.
- Разделительные строки для группировки по складам / клиентам.

**Т3. Формы выглядят «академически».**
`Input` использует один `h-9` для всех кейсов. Разделить:
- **Крупные формы** (регистрация, приёмка) — `h-11` + `text-lg`. Массовый пользователь не даёт себе труд промахнуться в 9px-полу.
- **Плотные табличные фильтры** — `h-8` + `text-sm`.

**Т4. Слабые affordance у кликабельных строк.**
Строки таблицы «Мой груз» открывают drawer, но визуально это простой `hover:bg-hover`. Добавить `chevron-right` в последней колонке — сигнал «здесь есть детали».

**Т5. Отсутствие иллюстрированного empty state.**
`EmptyState` — только текст. Легкая монолинейная SVG-иллюстрация («ящик», «маршрут», «весы») задала бы бренд. Не карикатурно, а в тон крафтовой палитры.

**Т6. Кнопка primary единственная (`bg-accent`) — она же и «отправить», и «удалить», и «сохранить курс».**
Опасные операции визуально не отделены. Ввести жёсткий контракт:
- `primary` — конструктивное действие.
- `danger` — деструктивное (уже есть variant `danger` в Button, но он не применяется в разделах вроде удаления клиента).
- `secondary` — «отмена».
Это уже частично есть — нужно доиспользовать.

**Т7. Цвета «горящий/не горящий/долг» плохо различимы для CVD.**
`--crit: #A63A2A` и `--warn: #A76A16` близки при протанопии. Добавить **иконки** (🔥 / ⚠️) параллельно цвету — двойной канал.

**Т8. Плотность и вертикальный ритм.**
`Density: dense | regular | airy` — грамотный контракт, но используется только пара таблиц. Овнеру-дашборду для 100+ строк нужна `dense` по умолчанию + user preference «густота».

**Т9. Числа выровнены справа, но заголовки — слева.**
Мелочь, но заголовки числовых колонок должны быть справа. В `Table.tsx` уже есть `align='right'` для header — проверить, что применяется во всех числовых колонках дашборда (`Dashboard.tsx`, `Debts.tsx`).

**Т10. Фокус-состояние клавиатурной навигации.**
`*:focus-visible { box-shadow: var(--shadow-focus,...) }` — использует переменную, но `--shadow-focus` не объявлена. Реально работает fallback `0 0 0 3px accent-tint`. Проверить — определить token, либо убрать fallback.

**Т11. Отсутствие визуального языка «финансовых цифр».**
На KPI суммы `0 с.` рисуются без разделителей тысяч. Убедиться, что `fmtSomoni` использует `Intl.NumberFormat('ru-RU', {style:'decimal', maximumFractionDigits:0})` (или локаль `ru-TJ`).

**Т12. Мобильная адаптация — только по грид-колонкам.**
Нет отдельного шаблона таблиц для узких экранов. Идея: на `< sm` таблицы «Мой груз» → карточки. Иначе горизонтальный скролл в кабинете клиента.

**Т13. Динамический контент внутри `PublicShell` меняется по `getToken()` — но `PublicShell` рендерится один раз при монтировании роутов.**
После login клиент возвращается на публичный экран, но шапка не перерендерится, пока не обновит страницу. Нужен reactive-стор (Zustand / React Context вокруг токена) — иначе кэш «В кабинет» показывается не сразу.

## 4. Security — итоги ручного скана

Aikido MCP требует sign-in и без подтверждения не даёт сканировать; semgrep/bandit локально не установлены. Ниже — ручной аудит по `main.py`, `deps.py`, `auth.py`, `clients.py`, `nginx.conf`, `docker-compose.yml`, `Dockerfile`, `client_codes.py`, `.env`.

### 🔴 P0

**S-1. Прод по HTTP.**
`http://77.42.41.16:8080` без TLS. JWT в `Authorization: Bearer` уходит в открытом виде. Пароли — тоже. MITM на публичном Wi-Fi = полный доступ.
**Fix:** Caddy/Traefik/nginx перед контейнерами + Let's Encrypt для `cargo.loik.tj` (или домена клиента). Http → https redirect. HSTS.

**S-2. Postgres и Redis торчат наружу.**
`docker compose ps` показал:
```
loik-postgres  0.0.0.0:5432->5432/tcp
loik-redis     0.0.0.0:6379->6379/tcp
```
Redis без пароля вообще. Postgres с `loik/loik_dev_password`. Это буквально «бери базу».
**Fix:** убрать `ports:` у `postgres` и `redis` в `docker-compose.yml` — им нужна только внутренняя сеть compose. Как минимум `127.0.0.1:5432:5432`.

**S-3. Дефолтный OWNER_PASSWORD не сменён.**
В `.env` на проде: `OWNER_PASSWORD=owner_change_me`. Совместно с S-1 (HTTPS нет) и P0-1 (никак не залогинить) получаем странную картину: реально попасть в кабинет овнера нельзя, но если исправить email — будет тривиальный dictionary-hit.
**Fix:** rotate + сделать `ensure_owner` идемпотентным, но НЕ переустанавливать пароль в существующем аккаунте (сейчас — не переустанавливает, но проверить).

**S-4. `.env` с prod-секретами лежит в рабочем каталоге и в бэкапе Windows.**
В файле:
- `SECRET_KEY=-MOdNa3EKo1VCpwACqDCaCTzjVa3t8EB-AtbOp6dYce0ReppkJ3j4EemriV5G1mk` — JWT-подпись.
- `TG_BOT_TOKEN=8999123991:AAFvURA2cb5pPuLzjkIHrVk6Mgo0t9oLrzc` — реальный prod-токен Telegram-бота.
- `POSTGRES_PASSWORD=loik_dev_password`.

`.env` в `.gitignore` — коммитов нет (git log чист), но:
- локальный файл будет распространён при экспорте проекта / скриншотах;
- **TG_BOT_TOKEN и SECRET_KEY нужно ротировать** — они уже упомянуты в этой переписке и в скринах логов.
**Fix:** revoke TG-токен у @BotFather, сгенерировать новый `SECRET_KEY` (`openssl rand -hex 64`), сменить `POSTGRES_PASSWORD`.

**S-5. `APP_DEBUG=true` в prod.**
`FastAPI(debug=True)` — трейсбеки в теле ответа + предзагрузка ORM-моделей. При ошибке 500 отдаётся полный stack trace, раскрывающий пути файлов и данные.
**Fix:** `APP_DEBUG=false` + `APP_ENV=prod`.

### 🟠 P1

**S-6. Слабые пароли клиента (min 6).**
При коде клиента `LQ-002` (энтропия угадывания — 3-4 цифры) и rate-limit-less API — брут-форс тривиален. NIST 800-63B: min 8, поощрять 12+.
**Fix:** min 8 (клиент), min 12 (staff), zxcvbn/entropy-check в UI.

**S-7. Нет rate-limit / lockout.**
Ни на `/auth/staff/login`, `/auth/client/login`, ни на `/clients/register`. Скрипт может брутить пароли или спамить регистрацию.
**Fix:** `slowapi` / `fastapi-limiter` + Redis (Redis уже поднят). По IP: `/auth/*` — 5/min. По коду клиента — 10/hour. На регистрацию — 3/hour per IP.

**S-8. JWT: 24 часа + отсутствие revoke / refresh.**
`JWT_ACCESS_TTL_MIN=1440`. Если токен утёк — нельзя отозвать. Нет refresh-token pattern → пользователь либо сидит 24 часа, либо каждые 15 минут перелогинивается.
**Fix:** access-TTL 15 мин + refresh-TTL 7 дней + `token_version` в БД для инвалидции.

**S-9. `HTTPBearer(auto_error=False)` не даёт единого 401 для отсутствующего токена.**
`get_current_principal` возвращает 401 с `no token`. Это ок, но токен также никогда не проверяется на алгоритм фиксацию: `python-jose` до 3.3.0 имел уязвимость к `alg=none`. У нас 3.3+, но нужно оставить white-list `[settings.jwt_alg]` (уже так — ок), плюс верифицировать `iat/exp` (`jose` делает).

**S-10. Отсутствуют security-заголовки в nginx.**
Ни `Strict-Transport-Security`, ни `X-Content-Type-Options: nosniff`, ни `Referrer-Policy: strict-origin-when-cross-origin`, ни `Permissions-Policy`. `Server: nginx/1.27.5` разглашает версию.
**Fix.** В `frontend/nginx.conf`:
```nginx
server_tokens off;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "geolocation=(), camera=(), microphone=()" always;
add_header Content-Security-Policy "
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
  font-src 'self' https://fonts.gstatic.com data:;
  img-src 'self' data: https://api.qrserver.com;
  connect-src 'self';
  base-uri 'self';
  frame-ancestors 'none';
" always;
# после HTTPS:
add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;
```

**S-11. JWT-токен в `localStorage`.**
XSS-vulnerable: любая инъекция скрипта уводит токен. Раньше уже нашлось, что `dangerouslySetInnerHTML/eval` в проекте нет — ок. Но защита должна быть в глубину: перейти на **httpOnly cookie** для access-token, `SameSite=Lax`.

**S-12. Внешние ресурсы под CSP.**
QR-код грузится с `api.qrserver.com` (в `TgVerify`). Google Fonts тоже. Это ОК, но CSP должен их явно разрешить (см. S-10). Также: **QR отправляет содержимое deep-link на сторонний сервис** — это ~безобидный tg-URL, но идеологически QR можно генерировать локально (`qrcode` в JS ~4KB) и не гонять на 3rd-party.

**S-13. `client_code` предсказуем.**
`LQ-001, LQ-002, ...` — при слабом пароле + отсутствии rate-limit угоняется. Идея: рандомизировать вторую часть (`LQ-A7K3`, 4 base32-символа, 20 бит) — сохраняет читаемость, добавляет 1млн вариантов.

**S-14. `bcrypt.gensalt(rounds=12)`** — норм. Хеш «клиент — 72 байта» с cutoff — ок, но при пароле > 72 байт `_prepare` тихо режет: пользователь ставит 100-байтный пароль, реально хешатся первые 72. Показывать warning в UI при длинных паролях, или использовать `argon2` (recommended).

### 🟡 P2

**S-15. Валидация email через `EmailStr` строгая по RFC 5321.**
`.local`, `.test`, `.example` отбрасываются (см. P0-1). Для B2B часто нужен «локальный». Решение: держать `.local`-домены только в dev-конфиге, или отключить `check_deliverability` в email-validator.

**S-16. `CORS_ORIGINS` пустой на проде.**
На сервере `CORS_ORIGINS=http://localhost:5173,http://localhost:3000` — заглушка. Работает потому что фронт nginx-проксирует `/api/`. Если кто-то заведёт мобильный клиент — нужно явно указать домен.

**S-17. `allow_credentials=True` + `allow_headers=["*"]` + `allow_methods=["*"]`**.
Пока origins фиксированы — не критично, но при неаккуратной смене origins на `*` получим CVE-like дыру. Явный whitelist.

**S-18. `.env` содержит `LOG_LEVEL=INFO` + логгеры `session.execute(...)` в debug.**
При `app_debug=true` SQLAlchemy `echo=True` (см. `db.py:15`). Все SQL-запросы, включая пароли (если бы они были в SQL, но они хешируются раньше). Оставляет PII в логах.

**S-19. Логи включают телефон и client_code**.
`log.info("зарегистрирован клиент %s", code)` — код в логах ок. Но в `staff_login` пишем `body.email` при ошибке. Утечка в мониторинге — GDPR / TJ Zakon o pers. dannykh.

**S-20. Bootstrap овнера в лайв-приложении.**
`ensure_owner()` в `lifespan` — при первом старте создаёт овнера. Если ошибка миграции — приложение поднимется без овнера, никто не заметит. Лучше вынести в CLI-команду.

### 🔵 P3

**S-21. Docker Dockerfile запускает от root.**
`FROM python:3.12-slim` без `USER app`. Уязвимость эскалации при RCE.

**S-22. `HEALTHCHECK` использует `curl`** — размер образа ↑, лишний depend. Можно `python -c "import urllib.request..."`.

**S-23. Node build без multi-stage cleanup ok, но кеш npm лежит в слое.**
Использовать `--prefer-offline` не нужно, но `RUN npm ci` вместо `npm install` для воспроизводимости.

**S-24. Логика ролей (`assert_own_warehouse`) корректная — овнер всегда `return`, остальные — сравнение `warehouse_id`.**
Но проверил только один вызов; убедиться, что все staff-эндпоинты, работающие со складом, вызывают `assert_own_warehouse`.

**S-25. Redis не используется как cache/session — почему он есть в compose?**
Если он резерв для APS-scheduler/rate-limit — задокументировать. Иначе — удалить.
